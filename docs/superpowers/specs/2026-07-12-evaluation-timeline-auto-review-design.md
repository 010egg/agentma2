# AgentMa 评测时间线与自动审核设计

日期：2026-07-12

状态：已批准，进入实现

范围：补全评测耗时与真实起止时间，并将证据审核简化为单项即时保存和自动完成。

## 1. 问题

当前候选排行只显示综合分、稳定性、Token 和成本，没有耗时。尝试记录虽然保存 `duration_ms` 和完成时间，但创建时间是在完成时写入，不能代表真实开始时间，因此无法解释一次运行为什么耗时较长。

审核工作台同时存在“提交用例审核”“提交单次审核”和“提交终审”三层按钮。审核人需要重复确认，运行是否已经就绪也不直观。

## 2. 已确认决策

- 候选排行显示平均耗时。
- 运行详情显示开始时间、结束时间和总墙钟时间。
- 每个“候选 × 用例”显示最早开始、最晚结束和聚合墙钟时间。
- 每次重复尝试显示真实开始时间、结束时间和执行耗时。
- 审核结论点击后立即保存，不再需要提交按钮。
- 默认审核单位仍为“候选 × 用例”；展开后可以单独覆盖某次重复尝试。
- 全部候选用例组形成明确人工结论后，运行自动完成并发布报告。
- `needs_attention`、多人审核冲突、结论未达到共识或保存失败都会阻止自动完成。
- 全部用例通过时运行结论为 `approved`；存在任一不通过时为 `rejected`，两种情况都生成完整报告。

## 3. 时间数据模型

### 3.1 作业时间

`evaluation_jobs` 新增：

- `started_at INTEGER`：Worker 成功领取作业时写入。
- `completed_at INTEGER`：作业进入 `completed`、`failed` 或 `cancelled` 时写入。

作业因租约过期重新排队时清空 `started_at`，下一次领取写入新的开始时间。重试仍属于同一个队列作业；尝试证据使用最终一次实际执行的起止时间。

### 3.2 尝试时间

`evaluation_attempts` 新增 `started_at INTEGER`。现有 `completed_at` 继续作为结束时间。创建成功或失败尝试时，从对应作业的 `started_at` 复制真实开始时间。

`duration_ms` 保留为执行器报告的有效执行耗时。界面同时展示墙钟跨度 `completed_at - started_at`，用于识别排队之外的外部等待、裁判或清理开销。两者差异明显时不互相覆盖。

### 3.3 旧数据

旧尝试没有 `started_at` 时不根据 `duration_ms` 倒推开始时间。开始时间显示 `-`，结束时间和执行耗时继续显示现有值，避免制造不真实时间线。

## 4. 时间聚合

### 4.1 候选排行

每个候选显示：

- `averageDurationMs`：该候选全部尝试的平均执行耗时。
- `wallClockDurationMs`：该候选最早尝试开始到最晚尝试结束的跨度；开始时间缺失时为 `null`。

排行主元数据使用“平均耗时”，悬停或展开信息展示总墙钟跨度。

### 4.2 候选用例组

审核矩阵的每个候选用例组增加：

- `startedAt`：组内有效尝试的最早开始时间。
- `completedAt`：组内尝试的最晚完成时间。
- `durationMs`：`completedAt - startedAt`；任一端缺失时为 `null`。
- `averageAttemptDurationMs`：组内尝试平均执行耗时。

### 4.3 运行

运行总耗时使用 `evaluation_runs.started_at` 到 `completed_at`。运行尚未完成时，结束位置使用当前时间并标记为“进行中”；页面轮询时同步更新。

## 5. 即时审核交互

### 5.1 单项状态

每个候选用例组和重复尝试维护独立保存状态：

- `idle`：未发生本地修改。
- `saving`：请求正在提交，控件暂时禁用。
- `saved`：服务器已确认，短暂显示已保存标记。
- `error`：保存失败，保留原服务器结论并显示重试入口。

点击 `approve`、`reject` 或 `needs_attention` 后立即调用现有细粒度审核 API。前端可以先显示待保存选择，但只有服务器成功后才更新报告中的最终结论。连续点击同一单项时，前一个请求完成后只提交最后一次选择，避免乱序响应覆盖新结论。

### 5.2 页面结构

- 审核矩阵单元格直接提供三个紧凑结论控件。
- 点击单元格仍可打开证据抽屉，但抽屉不再显示“提交用例审核”按钮。
- 重复尝试列表展开后提供相同的三个即时保存控件，不再显示“提交单次审核”按钮。
- 备注默认折叠。填写备注后，下一次结论保存同时提交备注；已有备注可单独打开编辑并通过即时保存更新。
- 移除运行详情中的“提交终审”区域和终审按钮。
- 页面顶部显示审核进度，例如“18 / 20 已明确，2 项需关注”。

## 6. 自动完成

每次用例级或尝试级审核写入成功后，后端在同一租户范围内重新计算运行审核矩阵。

运行满足以下条件时自动从 `awaiting_review` 转为 `completed`：

1. 矩阵至少包含一个候选用例组。
2. 每个组都有人工审核参与。
3. 每个组的有效结论为 `approve` 或 `reject`。
4. 没有 `needs_attention`、多人共识不足或审核冲突。

自动完成时：

- 任一组为 `reject`，`review_decision = rejected`。
- 全部组为 `approve`，`review_decision = approved`。
- `completed_at` 写入当前时间。
- 审核分配状态更新为 `submitted`。
- 写入自动完成审计事件，记录通过、不通过和总组数。

运行级 `evaluation_reviews` 和旧 `/review` API 保留兼容读取，但新页面不再调用。旧客户端仍可提交运行级终审；已自动完成的运行拒绝重复终审。

## 7. API 响应

报告与审核矩阵扩展时间字段，不新增独立时间接口：

```text
report.run.startedAt
report.run.completedAt
report.rankings[].averageDurationMs
report.rankings[].wallClockDurationMs
reviewMatrix.groups[].startedAt
reviewMatrix.groups[].completedAt
reviewMatrix.groups[].durationMs
reviewMatrix.groups[].averageAttemptDurationMs
reviewMatrix.groups[].attempts[].startedAt
reviewMatrix.groups[].attempts[].completedAt
reviewMatrix.groups[].attempts[].durationMs
```

细粒度审核写接口成功响应增加最新矩阵摘要和运行状态，使前端无需等待下一轮轮询判断是否已经自动完成。

## 8. 错误与并发处理

- 审核保存失败时不改变服务器结论，也不触发自动完成。
- 同一审核对象的请求按前端序列号和服务器创建时间排序，最后成功写入的事件生效。
- 两名审核人并发提交时仍按运行的 `single` 或 `consensus` 策略解析；共识不足保持待审核。
- 自动完成使用事务内条件更新，只允许 `awaiting_review` 状态转换一次。
- 已完成运行仍允许管理员查看证据，但默认不允许继续改判；后续若需要重开审核，应设计独立的“重新审核”流程，本次不实现。

## 9. 测试与验收

- 验证 Worker 领取、成功、失败、取消和租约恢复时的时间字段。
- 验证新尝试保存真实开始与结束时间，旧尝试开始时间保持空值。
- 验证候选、用例组、尝试和运行耗时聚合。
- 验证单项审核成功、失败、快速连续点击和重试状态。
- 验证所有组通过后自动完成并标记 `approved`。
- 验证存在不通过时自动完成并标记 `rejected`。
- 验证 `needs_attention`、未审核、多人冲突和共识不足阻止自动完成。
- 验证页面没有三个旧提交按钮，时间文本在桌面和移动视口不溢出。
- 运行定向 ESLint、生产构建、评测存储 smoke、评测 API smoke和配额回归。

## 10. 非目标

- 本次不补算旧运行的开始时间。
- 本次不修改 Token 和成本计价逻辑。
- 本次不增加甘特图或复杂时间可视化。
- 本次不实现已完成运行的重新打开审核。
- 本次不移除旧运行级审核表和兼容 API。
