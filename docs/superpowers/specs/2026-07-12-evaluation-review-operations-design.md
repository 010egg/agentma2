# AgentMa 评估系统审核与运维整改设计

日期：2026-07-12

状态：已通过总体设计，待用户审阅书面规格

范围：修正首版评估系统的候选调度、证据审核、项目统计、项目生命周期和候选标识。

## 1. 背景

首版评估系统已经能够创建项目、数据集、评分模板和运行，并产出候选排行及证据。但实际使用暴露出五个问题：候选执行看起来是串行的；证据只能在运行级一次性签署；通过率混合了全部项目；历史项目无法清理；默认“候选 A”无法识别 Agent 与模型。

本次采用在现有评测模块内增量补齐的方案，不重写评测引擎。原始尝试、自动评分和裁判结果保持不可变；人工结论作为独立记录叠加，保证历史可追溯。

## 2. 已确认决策

- 审核默认单位为“候选 × 用例”，同一候选对同一用例的多次重复执行先聚合展示。
- 审核人可以展开重复执行，并对某一次尝试单独覆盖聚合结论。
- 同一用例下的不同候选 Agent 应并行启动；实际并发受运行配置、租户配额和平台上限共同约束。
- 看板默认显示当前项目数据，可显式切换“全部项目”查看运维总览。
- 项目默认归档；租户管理员输入项目名称确认后可永久级联删除。存在活动运行的项目不可永久删除。
- 候选默认名称为“Agent 模板名称 · 模型名称”，允许附加用户别名。
- 运行级审核只控制报告是否正式发布，不再代替逐样本质量审核。

## 3. 调度与并发

### 3.1 并发模型

保留当前“候选 × 用例 × 重复序号”的执行作业粒度。运行新增可配置的 `concurrency`，其有效值为：

```text
effectiveConcurrency = min(runConcurrency, tenantAvailableConcurrency, platformConcurrencyCap)
```

创建运行时的默认值为候选数量，并限制在租户与平台当前允许的范围内。用户可以降低该值，不能通过页面配置突破平台上限。

### 3.2 公平领取

执行队列按运行和用例进行轮转。同一用例存在多个待执行候选时，Worker 优先领取不同候选，使横向对比尽早产生结果；不会先连续完成候选 A 的全部用例再执行候选 B。

全局 Worker 仍有平台并发上限，同时增加每个运行的活动作业计数。某个大型运行不能占满全部槽位并长期阻塞其他运行。裁判作业和候选执行作业分别计数，避免大量裁判任务阻塞尚未执行的候选。

### 3.3 可观察性

运行详情显示“运行中 / 本运行上限 / 平台上限”，并按候选展示排队、运行、完成和失败数量。并发受配额或平台限制时展示明确原因，不把等待状态表现为串行故障。

## 4. 细粒度审核

### 4.1 数据模型

新增两类不可变审核事件：

- `evaluation_case_reviews`：审核“运行 + 候选 + 用例”的聚合结果。
- `evaluation_attempt_reviews`：审核某一次具体重复执行。

每条记录保存租户、运行、候选、用例、可选尝试、审核人、结论、备注和创建时间。结论为 `approve`、`reject` 或 `needs_attention`。再次提交会新增记录，当前结论取该审核人对同一审核对象的最新记录，旧记录保留用于审计。

### 4.2 聚合规则

系统先读取每次尝试的自动与裁判结果，再应用最新的尝试级人工覆盖，形成每次尝试的有效结论。随后聚合同一“候选 × 用例”的重复执行：

- 没有人工用例结论时，按评分模板的重复策略聚合有效尝试；首版策略为多数通过，票数相同时不通过。
- 存在最新用例级人工结论时，该结论覆盖重复聚合结果。
- `needs_attention` 不计为通过，并进入待处理筛选。
- 人工覆盖只改变最终审核结论，不修改原始分数、模型输出、规则证据或裁判响应。

### 4.3 通过率口径

候选通过率按用例计算，而不是按重复尝试数量计算：

```text
candidatePassRate = passed candidate-case groups / reviewed-or-evaluable candidate-case groups
```

项目通过率按项目内所有已完成运行的候选用例组计算。运行级报告发布结论不进入质量通过率的分子或分母；它单独显示为“报告已发布 / 已驳回 / 待签署”。没有可评估结果时显示“暂无数据”，不显示 0%。

### 4.4 审核工作台

证据矩阵以用例为行、候选为列。每个单元格可以独立提交审核结论和备注，并显示自动判定、裁判判定、人工最终判定及分歧状态。展开单元格后列出重复尝试，允许单独改判某次尝试。

支持按未审核、失败、分歧、低置信度和需要关注筛选。批量操作仅作用于用户明确勾选的单元格，不提供“全部证据一键判对/判错”的隐式操作。

## 5. 项目范围与指标

页面维护一个明确的项目筛选状态。管理员进入评估系统时默认选择最近使用的未归档项目；没有最近记录时选择第一个未归档项目。筛选项包含“全部项目”，但它只用于队列、成本、运行量和失败量等运维总览。

当前项目下的 KPI 包括候选用例通过率、待审核单元格、完成运行、Token、成本和平均耗时。切换项目后，运行列表、排行、证据和 KPI 同步更新。前端不再使用已加载运行在浏览器内计算跨项目终审通过率；聚合由后端按租户和可选 `projectId` 查询，保证口径一致。

审核人只能看到被分配运行所属项目的数据，不能通过“全部项目”获得额外项目可见性。

## 6. 项目生命周期

### 6.1 归档与恢复

项目列表默认隐藏归档项目，可切换查看。归档不会删除数据，也不会影响历史报告；归档项目不能创建新运行，但可以恢复。运行中的项目可以归档，已有运行继续完成。

### 6.2 永久删除

永久删除仅限租户管理员。页面二次确认要求完整输入项目名称。后端再次检查名称、权限和项目状态，不能依赖前端确认。

当项目存在任何非终态运行时，返回 `409 project_has_active_runs`。非终态包括 `draft`、`queued`、`running`、`judging`、`awaiting_review` 和 `paused`；管理员需先取消或完成这些运行。检查通过后，在单个数据库事务中先删除项目运行，再删除项目。运行下的候选、作业、尝试、审核和报告数据按现有运行外键级联删除。

数据集、数据集版本、用例和评分模板是当前租户级共享资源，不随项目永久删除；仅删除运行中对这些资源的引用。归档、恢复和永久删除均写入审计日志，其中永久删除日志只保存项目标识、名称、类型和删除数量摘要，不保留被删除证据内容。

## 7. 候选标识

创建在线候选时，服务端从可见 Agent 模板生成不可变快照，并计算基础名称：

```text
candidateName = `${agentTemplateName} · ${modelDisplayName}`
```

`candidateAlias` 单独保存。界面主标题始终显示基础名称；用户别名作为辅助标签展示，避免别名再次隐藏真实配置。离线候选没有 Agent 模板时使用“离线候选名称 · 来源标识”。

名称由服务端快照生成，前端不再初始化“候选 A”。模板或模型以后改名不会影响历史运行。裁判 Agent 继续只接收匿名候选编号，避免品牌偏差。

## 8. API 变更

新增或扩展以下接口：

```text
GET    /api/evaluations/overview?projectId=<id|all>
PATCH  /api/evaluations/projects/:id/archive
PATCH  /api/evaluations/projects/:id/restore
DELETE /api/evaluations/projects/:id
GET    /api/evaluations/runs/:id/review-matrix
POST   /api/evaluations/runs/:id/case-reviews
POST   /api/evaluations/runs/:id/attempt-reviews
```

删除接口请求体包含 `confirmationName`。审核写接口要求调用者是租户管理员或该运行的指定审核人，并验证候选、用例和尝试均属于同一运行。所有写操作使用现有错误响应格式和审计机制。

运行创建接口接受 `concurrency` 和可选 `candidateAlias`。服务端负责计算最终候选快照名称与有效并发，客户端提交的展示名称不能覆盖真实模板和模型标识。

## 9. 兼容与迁移

数据库升级采用幂等建表和增列，不修改已有尝试和运行。旧候选如果只有 `name`，报告继续显示旧值；新候选同时保存模板名、模型显示名和别名。读取层对旧记录提供兼容映射。

旧运行没有细粒度审核记录时，候选用例结论从现有尝试结果派生。旧的运行级 `evaluation_reviews` 继续作为报告发布记录展示，不反向伪造逐样本审核。这样升级后历史报告可读，同时不会把一次运行签署误算成所有样本都通过。

## 10. 错误处理

- 并发值越界返回 `invalid_concurrency`，同时返回允许范围。
- 审核对象不属于运行返回 `not_found`，避免泄露其他项目数据。
- 已取消、失败或尚未产生证据的尝试不能提交通过/不通过审核。
- 并发任务失败只影响对应尝试，其他候选继续执行。
- 永久删除与状态变化竞争时依赖事务内二次检查；检查失败不删除任何数据。
- 聚合统计查询失败时页面保留上一次成功结果并提示刷新，不回退到浏览器端混合口径。

## 11. 测试与验收

### 11.1 存储与 API

- 验证用例级和尝试级审核的最新事件覆盖、历史保留和租户隔离。
- 验证尝试级覆盖后，用例聚合与候选通过率正确变化。
- 验证项目筛选后 KPI、运行和证据均属于指定项目。
- 验证归档、恢复、名称确认、活动运行拦截和永久级联删除。
- 验证旧运行、旧候选名称和运行级审核仍可读取。

### 11.2 调度

- 使用可控的延迟候选证明同一用例的多个候选存在重叠执行时间。
- 验证本运行上限、租户上限和平台上限三者取最小值。
- 验证两个运行同时排队时都能获得执行槽位。
- 验证执行作业与裁判作业不会互相长期饥饿。

### 11.3 前端

- 证据单元格可逐个审核，重复尝试可展开并单独覆盖。
- 项目切换同步更新全部项目级内容，刷新后保留最近项目。
- 删除弹窗必须输入完整项目名，活动项目显示不可删除原因。
- 候选在创建、运行、排行、证据和报告中均显示模板名与模型名。
- 桌面和移动视口无文字重叠，审核矩阵在窄屏可横向滚动且操作列保持可用。

### 11.4 发布验证

运行定向 ESLint、生产构建、评测存储 smoke、评测 API smoke、配额回归和浏览器流程检查。部署后重启 `ai.agentma2.dashboard`，确认未登录评测 API 返回 `401`，登录后完成创建项目、并行运行、逐样本审核、项目筛选、归档及删除的完整流程。

## 12. 非目标

- 本次不重写为分布式队列，也不引入 Redis 或消息中间件。
- 本次不支持恢复已永久删除的项目。
- 本次不改变自动规则和裁判 Agent 的评分算法。
- 本次不把运行级发布签署移除；只将它与样本质量审核分离。
- 本次不提供跨项目共享数据集或评分模板的新能力。
