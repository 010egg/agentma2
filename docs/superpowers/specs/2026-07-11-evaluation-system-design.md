# AgentMa 评估系统设计

日期：2026-07-11

状态：待用户审阅

范围：运维模块中的统一评估系统

## 1. 背景与目标

AgentMa 目前已有 Agent 模板、模型选择、会话运行、租户权限、配额、审计和 SQLite 持久化能力，但缺少可重复、可比较、可追溯的质量评估流程。

本模块在运维区新增“评估系统”，同时支持两类评测：

1. **代码修复评测**：让多个 Agent 与模型组合修复同一个代码问题，通过构建、测试、静态检查、裁判 Agent 和人工审核综合判定。
2. **问答评估**：让多个 Agent 与模型组合回答同一批问题，通过标准答案、关键词、引用材料、结构化断言、裁判 Agent 和人工审核综合判定。

两类评测共用项目、测试集、候选配置、运行队列、评分模板、审核、报告和审计，只在输入形式、执行器和自动验证指标上使用不同适配器。

首版容量目标为单次约 1,000 个用例、最多 10 个候选，支持排队和受控并发，不建设分布式调度平台。

## 2. 已确认的产品决策

- 评测类型同时包含 `code_repair` 和 `qa`。
- 判定流程采用“自动验证 → 裁判 Agent → 人工终审”。
- 候选既可由系统在线运行，也可从外部离线导入。
- 测试集既可在页面逐条创建，也可通过 JSON、JSONL 或 CSV 批量导入，并保存为可复用版本。
- 在线候选可配置任意“Agent + 模型”组合，并允许重复运行以衡量稳定性。
- 评分模板提供代码修复和问答预设，同时允许调整指标、权重、通过阈值和裁判提示词。
- 代码项目支持 Git 仓库与 ZIP/TAR 压缩包，每个候选使用独立隔离工作区。
- 构建、测试和静态检查命令由系统识别并给出建议，运维人员确认或修改后才执行。
- 问答用例可选填标准答案、关键词、引用材料和结构化断言；缺失部分由规则与裁判 Agent 补足。
- 人工终审支持管理员、指定审核人和多人复核，并可选择一人通过或多人共识。

## 3. 设计原则

### 3.1 统一核心，隔离差异

公共生命周期由评测核心管理。代码仓库准备、命令执行、补丁收集属于代码修复适配器；答案解析、引用检查、结构化断言属于问答适配器。适配器通过稳定接口返回统一的候选提交、指标结果和证据。

### 3.2 原始证据不可覆盖

模型输出、补丁、命令日志、退出码、规则结果和裁判原始响应均作为不可变证据保存。重新评分生成新的评分版本，不修改旧记录。人工改判必须填写原因并进入审计日志。

### 3.3 可复现优先

正式运行冻结以下快照：测试集版本、候选 Agent 配置、模型、评分模板、裁判配置、项目提交、验证命令和运行参数。后续修改配置不会改变历史运行。

### 3.4 安全优先

代码修复任务可能包含不可信仓库和命令。Web 服务不得直接在宿主机执行评测命令。所有代码执行必须进入隔离执行器，并受到时间、CPU、内存、磁盘、网络和进程数量限制。生产环境未配置合格隔离器时，系统必须拒绝启动代码修复评测，而不是降级为宿主机执行。

## 4. 总体架构

```text
页面录入 / 数据集导入 / 在线候选 / 离线候选
                       │
                       ▼
                 统一评测核心
       ┌───────────────┴───────────────┐
       ▼                               ▼
代码修复适配器                    问答评估适配器
仓库、沙箱、命令、补丁            答案、断言、引用、格式
       └───────────────┬───────────────┘
                       ▼
        自动验证 → 裁判 Agent → 人工终审
                       │
                       ▼
                 报告、导出、审计
```

### 4.1 前端

在现有 React 应用中新增评估系统路由和页面，复用现有卡片、表单、状态徽标、模型选择器和权限上下文。

### 4.2 API 与领域服务

Express API 只负责鉴权、参数校验、资源访问和调度命令。评测领域逻辑放入独立服务文件，避免继续扩大 `server.ts`：

- `evaluation-service`：项目、测试集、运行和报告生命周期。
- `evaluation-queue`：任务领取、租约、重试、取消和并发控制。
- `code-repair-adapter`：仓库准备、命令建议、沙箱执行和补丁采集。
- `qa-adapter`：断言执行、答案证据和引用检查。
- `judge-service`：裁判请求、结构化响应、盲评和重试。
- `review-service`：任务分配、多人共识、改判与最终签署。

### 4.3 持久化

继续使用现有 `node:sqlite` 存储。队列采用数据库任务表和租约机制，不引入 Redis、RabbitMQ 或外部调度系统。大体积补丁、日志和导入文件写入受控的租户工件目录，数据库只保存元数据、摘要、校验值和相对路径。

### 4.4 Worker

评测 Worker 与 HTTP 请求解耦。首版可与服务进程一起部署，但通过独立循环领取数据库任务，且接口允许未来拆为单独进程。Worker 崩溃后，超过租约时间的任务可重新入队。

## 5. 核心领域模型

### 5.1 评测项目 `evaluation_projects`

保存名称、描述、评测类型、负责人、默认评分模板、可见范围和归档状态。项目是测试集与多次运行的长期容器。

### 5.2 测试集与版本

- `evaluation_datasets`：测试集身份、类型、名称和创建者。
- `evaluation_dataset_versions`：不可变版本、导入来源、字段映射、用例数和校验摘要。
- `evaluation_cases`：属于某个版本的具体用例。

代码修复用例包含问题说明、仓库来源、基准提交、可选测试补丁、命令建议和限制。问答用例包含问题、可选标准答案、关键词、引用材料、结构化断言、标签和难度。

### 5.3 候选配置 `evaluation_candidates`

候选来源为：

- `online`：冻结 Agent 模板快照、模型、参数和重复次数。
- `offline`：保存导入批次、候选标识、外部输出与字段映射。

同一运行内的候选使用匿名编号交给裁判，避免名称和模型品牌影响判断。

### 5.4 运行与作业

- `evaluation_runs`：一次正式评测，关联冻结的数据集、候选和评分配置。
- `evaluation_jobs`：队列中的最小调度单元。
- `evaluation_attempts`：一个候选对一个用例的一次实际尝试。
- `evaluation_artifacts`：答案、补丁、日志、图片、报告等工件。

作业以“运行 × 候选 × 用例 × 重复序号”为基本粒度，便于失败重试和局部重跑。大规模创建时分批插入作业，避免一次事务锁住数据库过久。

### 5.5 评分与审核

- `evaluation_rubrics` 与 `evaluation_rubric_versions`：评分模板和不可变版本。
- `evaluation_metric_results`：自动指标及其证据。
- `evaluation_judgements`：裁判 Agent 的结构化评分、理由、置信度和原始响应引用。
- `evaluation_review_assignments`：审核人、状态和截止时间。
- `evaluation_reviews`：人工评分、改判、备注和签署结果。
- `evaluation_audit_events`：关键操作审计。

所有表均包含 `tenant_id`；所有读取和写入必须在租户范围内执行。

## 6. 运行状态与数据流

### 6.1 顶层运行状态

```text
draft
  → validating
  → queued
  → running
  → judging
  → awaiting_review
  → completed
```

辅助状态包括可恢复的 `paused`，以及终态 `failed`、`cancelled` 和 `archived`。取消会阻止新任务领取，并向正在运行的执行器发送协作取消信号；已经产生的证据仍然保留。

### 6.2 创建与预检

1. 运维人员选择评测类型和测试集版本。
2. 配置在线候选或导入离线候选。
3. 选择评分模板、裁判 Agent、审核策略、并发和预算。
4. 系统执行预检：字段完整性、Agent/模型可用性、项目来源、命令建议、沙箱状态、用例数量和预计任务数。
5. 运维人员确认后冻结快照并启动运行。

### 6.3 在线执行

问答候选复用现有 Agent 运行能力，但由评测 Worker 调用领域级运行接口，不通过浏览器会话模拟。代码候选由代码修复适配器创建隔离工作区，将基准项目复制或检出到工作区，运行 Agent，再执行已确认的验证命令。

每次尝试保存开始时间、结束时间、模型、Token、成本、工具调用摘要、输出、错误类型和工件引用。重复运行分别保存，然后计算均值、标准差、成功率和最差表现。

### 6.4 离线导入

导入向导先展示字段映射和前若干行预览。每条记录必须能映射到唯一用例与候选。重复键、缺失用例、非法补丁和无法解析的结构化结果进入错误清单；有效记录可以在用户确认后部分导入。

离线结果跳过在线生成阶段，但仍进入相同的自动验证、裁判和人工终审流水线。若离线包未包含执行所需项目或证据，系统只执行能够成立的指标，并明确标为“不可验证”，不得自动记为通过。

## 7. 自动验证与评分

### 7.1 代码修复预设指标

- 项目准备是否成功。
- 构建命令退出码与耗时。
- 原始测试、隐藏测试和回归测试的通过数量与比例。
- lint、类型检查和静态分析结果。
- 补丁大小、变更文件数和是否修改禁止路径。
- 超时、资源超限和异常退出。

“必须通过”的指标属于硬门槛。候选即使加权总分较高，只要违反硬门槛，也不能自动判为通过。

命令识别只产生建议：例如根据 `package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml` 等文件推断安装、构建和测试命令。正式运行只使用运维人员确认后的命令快照。

### 7.2 问答预设指标

- 精确匹配或归一化匹配。
- 必含、可选和禁用关键词。
- 正则、枚举、数值范围和 JSON Schema 等结构化断言。
- 引用是否存在、是否指向给定材料、引用片段是否支持结论。
- 格式、长度、语言和必需章节。
- 回答完整性及拒答合理性。

首版不允许测试集携带任意 JavaScript 或 Shell 断言，避免通过评测数据执行不可信代码。

### 7.3 裁判 Agent

裁判输入包括题目、必要上下文、评分量表、候选输出和自动验证摘要，不包含候选名称、模型品牌和创建者。输出必须符合版本化 JSON Schema，至少包含逐项分数、理由、证据引用、置信度和异常标记。

为控制约 10 个候选时的成本，默认使用逐候选评分；仅在前列候选分差小于模板阈值时，对前若干名执行成对复判。裁判请求失败可按配置重试，连续失败后进入人工处理，而不是编造分数。

### 7.4 总分

所有可计分指标归一化到 0–100。评分模板定义自动指标和裁判指标的权重、硬门槛、缺失指标处理和通过阈值。系统保存计算明细，报告中的总分必须可回溯到每一个指标。

人工审核可以维持结果、调整分数、判为通过/不通过或要求局部重跑。任何人工覆盖都必须填写理由，且报告同时显示机器建议与最终决定。

## 8. 人工终审

运行进入 `awaiting_review` 后生成审核任务。策略包括：

- **一人通过**：任一指定审核人签署后完成。
- **多人共识**：达到配置人数且结论一致后完成；发生分歧时交由管理员仲裁。

人工终审是运行级发布门禁，不要求审核人逐条手动打分。审核工作台优先展示：自动验证与裁判冲突、低置信度、硬门槛失败、候选分差过小、随机抽样以及被人工标记的用例。审核人可继续展开所有用例证据。

运维管理员可创建和管理评测。`team_admin` 或 `member` 只有在被分配审核任务时才能访问对应运行的只读证据和提交审核结论，不能修改测试集、候选或评分模板。

## 9. 页面与交互设计

### 9.1 导航与权限

侧边栏运维区新增“评估系统”。租户管理员始终可见；被分配审核任务的普通成员可见受限入口。前端可见性只改善体验，后端仍逐个 API 校验资源权限。

### 9.2 页面结构

1. **评测总览**：运行数量、通过率、待审核数、队列深度、近期失败、Token 与成本趋势。
2. **评测项目**：项目列表、类型、负责人、最近运行和归档操作。
3. **测试集**：版本列表、手工编辑、批量导入、字段映射、校验错误和用例预览。
4. **评分模板**：代码修复/问答预设、指标权重、硬门槛、裁判配置和版本历史。
5. **新建运行向导**：类型与数据集 → 候选 → 执行与命令 → 评分与裁判 → 审核与预算 → 预检确认。
6. **运行详情**：概览、候选排行、用例矩阵、实时任务状态、失败分类、日志和工件。
7. **审核工作台**：待处理队列、风险用例、证据对照、评分覆盖、评论和签署。
8. **报告**：候选排名、置信区间、稳定性、成本/耗时、分项指标、失败聚类和最终审核记录。

### 9.3 运行详情交互

默认展示候选汇总表。用例矩阵以候选为列、用例为行，通过筛选器查看失败、分歧、低置信度和待审核项。点击单元格打开证据抽屉：问答显示问题、依据、回答、断言和裁判理由；代码修复显示问题、补丁、命令、日志和测试差异。

运行期间通过轮询获取进度；首版不依赖新增 WebSocket 协议。进度数据按状态聚合，详情日志按需加载，避免一次返回上万个尝试对象。

建议按资源拆分 API：

```text

/api/evaluations/datasets/:id/versions
/api/evaluations/rubrics
/api/evaluations/runs
/api/evaluations/runs/:id/start
/api/evaluations/runs/:id/cancel

/api/evaluations/runs/:id/summary
```

列表接口使用游标或页码分页；尝试详情、日志和工件独立加载。创建、启动、取消、重试、改判和签署均写入现有审计系统。

## 11. 隔离、配额与安全

### 11.1 隔离执行器

执行器采用接口抽象，首选容器或受控 OS 沙箱实现。每次尝试获得独立工作目录和临时凭据，并在完成后按保留策略清理。默认禁止外网；确需安装依赖时，只能使用任务明确允许的网络策略和代理源。

以下内容必须限制：最大墙钟时间、CPU、内存、磁盘、子进程、输出日志大小、文件路径、环境变量和网络。仓库中的配置不得覆盖平台安全限制。

### 11.2 配额

创建运行时估算任务数和最大预算。运行级限制包括并发数、最大 Token、最大成本、最大尝试次数和总墙钟时间。达到预算后不再领取新任务，运行进入 `paused` 并记录 `budget_exceeded` 原因，等待管理员取消，或提高预算后恢复排队。

### 11.3 敏感信息

报告和日志写入前执行凭据模式脱敏。裁判 Agent 只接收评分所需内容。工件下载使用鉴权 API，不暴露真实文件系统路径。

## 12. 错误处理与恢复

错误分为可重试和不可重试两类：

- 可重试：模型限流、短暂网络错误、Worker 丢失租约、裁判输出格式错误。
- 不可重试：数据集无效、基准提交不存在、命令被安全策略拒绝、断言配置错误、工件校验失败。

单个尝试失败不应让整次运行立即终止。系统按失败类别继续其他作业，并在超过运行级失败阈值时停止领取新任务。管理员可以仅重跑失败尝试；重跑创建新尝试记录并保留旧证据。

Worker 通过租约和心跳避免任务永久卡在 `running`。服务重启后重新领取过期任务。关键状态转换使用事务和条件更新，防止重复启动、重复签署或取消后继续入队。

## 13. 报告与导出

最终报告至少包含：

- 候选总排名、通过率和分项指标。
- 重复运行的均值、标准差、最好与最差结果。
- 质量、耗时、Token 和成本对比。
- 自动验证与裁判 Agent 的分歧情况。
- 失败类别和代表性用例。
- 人工审核人、结论、改判理由和签署时间。
- 可复现快照标识。

首版支持页面查看和 JSON/CSV 导出。PDF 报告不进入首版范围，待页面报告稳定后再增加。

## 14. 测试策略

### 14.1 单元测试

- 数据集导入、字段映射和校验。
- 权重归一化、硬门槛、缺失指标和总分计算。
- 状态机、租约、重试、取消和预算判断。
- 审核权限、共识计算和改判审计。
- 裁判响应 Schema 校验及盲化处理。

### 14.2 集成测试

- 在线问答候选从运行到最终报告的完整链路。
- 离线结果导入后进入统一评分流水线。
- 代码修复在假执行器中的仓库准备、命令运行、补丁和日志采集。
- Worker 崩溃、租约过期和服务重启后的恢复。
- 租户隔离、普通审核人越权和工件下载鉴权。

### 14.3 安全测试

- 路径穿越、压缩包炸弹、符号链接逃逸和超大日志。
- 命令注入、环境变量泄露和网络访问限制。
- 恶意裁判内容、提示注入和结构化输出绕过。

### 14.4 验收场景

1. 创建含 100 个问答用例和 3 个在线候选的运行，完成自动评分、裁判、多人审核和报告导出。
2. 导入同一测试集的离线回答，和在线候选出现在同一排行中。
3. 对 Git 项目创建代码修复运行，每个候选使用独立沙箱，报告可查看补丁、测试结果和资源消耗。
4. 取消运行后不再领取新作业，重启服务后不存在永久卡住的任务。
5. 普通成员只能访问分配给自己的审核任务，不能修改评测配置或查看其他租户数据。

## 15. 首版范围与非目标

首版包含统一评测核心、两类适配器、在线/离线候选、数据集版本、数据库队列、自动验证、裁判 Agent、多人终审、报告和导出。

首版明确不包含：

- 多机分布式 Worker 和外部消息队列。
- 公共 Benchmark 市场。
- 用户上传任意评分代码或插件。
- 自动定时回归和发布流水线门禁。
- PDF 报告和跨租户共享。

这些能力应在首版数据模型和服务接口上保留扩展空间，但不提前实现。

## 16. 实施边界

实施时应将本模块拆为聚焦的领域文件和页面组件，不把全部逻辑继续堆入 `dashboard/server.ts`、`dashboard/server-store.ts` 或单个大型 React 页面。数据库迁移必须向后兼容现有数据；现有会话与 Agent 运行行为不因评估模块而改变。

设计获得确认后，下一步单独编写实施计划，按“领域模型与迁移 → API 与队列 → 两类适配器 → 裁判与审核 → 页面与报告 → 安全及端到端验证”的顺序交付。
